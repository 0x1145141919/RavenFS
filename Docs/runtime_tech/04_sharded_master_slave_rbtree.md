## 0. 一句话总纲

> **FS_block 的运行时分配器，从「全量内存位图 + 分片 + 位扫」改制为
> 「多分片 + 每分片一棵主从红黑树」：主树按区间位置（by_pos）作户籍，
> 从树按区间尺寸（by_size）作派生索引，同一批侵入式 `free_interval` 区间双挂；
> 片内一把锁保原子性，片与片零共享。**
> —— 磁盘契约层仍是位图，本设想只改运行时。

## 1. 设想的由来：两套位图的语义不对称

用户 2026-10-03 00:29 起的观察（会话 [5]）：

> 突然意识到怎么感觉上了内存考虑重新解释为红黑树更好？block 位图变成 free_interval 红黑树，
> 反正全局一张坐标无歧义，并且块区间分配的那叫一个重视的是分配的时候有没有连续的，
> 返还的时候避免碎片。inode_bitmap 只会一个一个分配/释放，反而看不出上空闲区间红黑树。

拆出两条判据：

| 世界 | 分配粒度 | 真正在乎的 | 位图是否精确匹配 |
|---|---|---|---|
| FS_block | **区间**（连续 N 块） | 分配找连续、释放防碎片 → 邻接合并 | ❌ 把「连续」打碎成 bit |
| inode | **单个** | 「给我一个空闲编号」 | ✅ 天然精确 |

**结论（设想的第一刀）**：同一套位图结构被硬套到两种不同粒度的分配器上，只因「都长得像位图」。
FS_block 该换成**区间结构**；inode 世界另议（见 §2.6）。

## 2. 设想分解

### 2.1 FS_block：位图 → free_interval 区间集合

内存表示（设想 [5]）：

```
节点 = { fblkbase, len }     // 一段连续空闲区间
坐标 = fblkbase 全局唯一     // 「全局一张坐标无歧义」，无需「bit 号 = 块号」的隐式约定
```

- **分配 N 块**：找第一个 `len ≥ N` 的区间 → 切走前 N 块 → 剩余区间原地更新。
- **释放 [base, len]**：查左右邻居（前序/后继），能合并即合并 —— 这是位图做不到的 O(log n) 邻接合并。
- 副产品：**不再需要尾巴补 1 那类补丁**（区间是显式的，不靠「隐含恒等映射」自证）。

### 2.2 双索引：同一区间挂两棵侵入式红黑树

用户 00:32（会话 [7]）：

> 关键是我想到的是一个区间属于两种侵入性红黑树，一个是区间大小排行红黑树，
> 一个是区间位置排行，你看成吗？

```
struct free_interval {
    uint64_t base;
    uint64_t len;
    struct rb_node by_pos;    // key = base        —— 区间位置排行
    struct rb_node by_size;   // key = (len, base) —— 区间大小排行
};
```

- 同一 `free_interval` **自己长两个 rb_node**，同时挂两棵树 —— 即「侵入式」：
  节点不是容器元素，索引钩子长在区间对象自己身上（融合时是对象级操作，**分配路径零 malloc**）。
- 两个查询维度天然正交：
  - `by_size.lower_bound((N,0))` → 直接回答 alloc(N)「哪个区间够大」
  - `by_pos.predecessor(base)` / `successor(base+len)` → 直接回答 free「左右邻居是谁、能不能合并」

> **AI 审查（判定成立）**：这是经典的 dual-index free-list 设计（Linux buddy / SLUB partial list /
> ZFS spacemap 都摸过）。**唯一要钉死**：`len` 会重复，by_size 的 key 必须取 `(len, base)` 复合，
> 否则红黑树 key 不唯一。

### 2.3 主从红黑树架构（设想核心）

用户 01:48（会话 [15]）：

> 主从红黑树架构，对，主红黑树为区间序，从红黑树（侵入式）为尺寸，区间序列。
> 返还的时候先预判合并还是什么，不合并就先主红黑树先插入，再插入从红黑树。
> 发生融合就先预先删除被波及节点的主红黑树户籍，然后融合，重插入。
> 当然都是在分片的锁下保护原子性。

角色分配：

```
主树 by_pos  : key = base        ← 户籍 / 唯一真相源，定义 free_interval 的存在性
从树 by_size : key = (len, base) ← 派生索引，只回答「哪个 len 够大」
```

**这是设想里最关键的一手**：两棵树**不是对等双树**，而是主从。于是——

- invariant 是**单向**的：`by_size 的每个节点 ∈ by_pos 的节点集合`（从 ⊆ 主）
- `by_pos` 是权威，`by_size` 出问题可**直接重建**
- 融合时**先从后主**地删除，保证「从 ⊆ 主」在**每个指令边界**都成立
  （不依赖「锁内中间态不可观测」这种隐含假设）

free 流程（设想原话 → 形式化）：

```
free([base,len]):
  锁分片
  主树查 predecessor(base) / successor(base+len)     ← 「先预判」
  分支 A（不合并）: 主树插入 → 从树插入
  分支 B（融合）  : 先删被波及节点（从树先删，主树后删）
                    → 融合成新区间
                    → 主树重插 → 从树重插
  解锁
```

### 2.4 分片（并发度来源）

用户 01:39（会话 [13]）：

> 位图可以分片，我红黑树何不能分片。

- **分片切的是 key 空间，与底层结构正交** —— 位图能切，红黑树照切。
- 分片 s 负责 FS_block 区间 `[s×S, (s+1)×S)`，片内一套主从树，**一把片锁**。
- `free_interval` 天然落在某个分片（`base` 决定归属）。
- **并发度上界 = 分片数**，与「分片位图」同阶。
- 副作用（正面）：原先担心的「内存随碎片浮动、可能爆」，**分片后每片 F_s 被 S 限制，上限可预测**。

> **AI 审查**：此问拆掉了「双树并发打不过位图」的论证——之前是拿「单树 vs 分片位图」在比，偷换了。
> 正确对比是「分片双树 vs 分片位图」，同量级。双树真正的门槛不在并发，在
> **片内两树同步**与**跨片合并的区间归属**两条 invariant（见 §5）。

### 2.5 定期落地：分片可冻结→写回

用户 01:48（会话 [15] 末）与 01:53（会话 [17]）：

> 并且使用分片也可以进行维护，定时全量冻结分片，写回磁盘，如何？

> 对，内存里面飞行太久不完全好

设想要点：

- 内存态**不能是唯一真相源**——飞太久，崩溃即全丢，且丢的是**元数据的分配状态**（丢了整个盘成谜题）。
- 解法：**分片定期落地**（checkpoint）。位图 = checkpoint，双树 = 易失的运行时加速层。
- 「冻结」不必全局：可**逐分片**冻结、逐片写回，把停顿切碎成「每片一次小停顿」。

### 2.6 inode 世界

用户 02:02（会话 [25]）：

> 所以说我看 inode 位图重新解释为多分片的已分配节点的引索红黑树？
> 分配就是每个分片找一个不冲突的引索。

> **AI 审查（修正）**：红黑树是**有序集合**，回答不了「给我一个不在集合里的编号」（补集查询）。
> 「已分配索引树」不成立。**正确且对称的形态**是：
> **inode 也走「空闲区间」树，但只需一棵 by_pos ——不需要 by_size**（因为 inode 分配永远是「一个」，
> 没有「找 ≥ N」的需求）。
>
> | | FS_block | inode |
> |---|---|---|
> | 分配粒度 | 区间 | 单个 |
> | 查询维度 | 位置 + 大小（**双树**） | 只需位置（**单树**） |
> | 分片 / 持久契约 | 是 / 位图 | 是 / 位图 |
>
> 收益 = **两个世界结构对称 + 代码共享**（同一套分片框架 / 锁 / checkpoint，inode 少一棵从树）；
> 代价 = inode alloc 从 O(1) ffz 变为 O(log F_s)（文件数不爆的场景无感）。
> —— 用户未确认此修正，**列为待拍板**（§5.P4）。

## 3. 核心纪律：磁盘契约 ≠ 运行时实现

用户 01:58（会话 [19]）——**本设想最重要的一条边界论断**：

> 不不不，磁盘契约和运行时实现是两码事。

用户 02:06（会话 [27]）进一步封死：

> 这仍然是运行时策略。虽然理论上说磁盘上也能用 B+树描述空闲区段，但是一致性难评，自指难。

| 层 | 内容 | 性质 |
|---|---|---|
| **磁盘契约** | 位图（FS_block 位图 + inode 位图） | 持久、自描述、唯一真相源；`bit[i]=1` 即已分配 |
| **运行时实现** | 多分片主从红黑树（本文设想） | 易失、可重建、不承担持久化责任 |

- 磁盘上**不放树**。放树则两难自证：
  - **一致性难评**：树的节点改动与位图的改动无法原子（无事务），崩溃必炸；
  - **自指难**：树描述空闲区段，但树自己也占块 → 要在位图亮灯 → 位图又描述树 → 递归。
- 位图天然无此问题：**自指被静态化**（mkfs 时位图区间预置全 1，此后不变），不随时间变化即不再是递归。
- **层间接口只有一个**：挂载时 `位图 → 重建双树`；写回时只写位图。接口窄，层内自由。
- 用户 02:11（会话 [31]）为这条边界给出**根本理由**（位图的「笨优势」）：
  > 位图机制虽然死板、比灵活的动态树花更多内存，却更容易自指自包含自洽，
  > 能够 0 冗余几何推导，并且元数据开销实在是小。
  >
  > | 维度 | 位图 | 动态树 |
  > |---|---|---|
  > | 自指 | 静态化，常量边界 | 动态递归，难解 |
  > | 位置 | 几何推导，0 冗余 | 必须落盘根指针 |
  > | 空间 | 恒定，有上界 | 浮动，最坏无上界 |
  > | 自包含 | 是，损坏隔离到 bit | 否，节点损坏波及子树 |
  > | 崩溃恢复 | 读它就行 | 依赖全树完整 |
  > | **契约资格** | ✅ | ❌ |

**本文据此定位**：设想再优秀，也只存在于运行时域；`disk_layout` 的位图契约不动。

## 4. 落地形态（讨论收敛后的自洽版本）

```
运行时（内存，分片）:
  分片 s: [s×S, (s+1)×S)，一把锁
    FS_block:  主树 by_pos(key=base) + 从树 by_size(key=(len,base))   // 双树，从 ⊆ 主
    inode:     单树 by_pos(key=base)                                  // 待拍板 P4

alloc(N):
  锁分片 → by_size.lower_bound((N,0)) → 命中 → 切分 → 主/从树同步 → 解锁
  （失败：片内无满足段 → 报错；跨片不拼接）

free([base,len]):
  锁分片 → 先预判 → A 纯插入 / B 先删(从先主后)再融合再重插 → 解锁

持久化（位图为契约）:
  挂载: 读位图 → 逐分片重建双树/单树
  写回: 只写位图（时机/原子性 = 实现取舍，不写进契约）

恢复:
  读位图 → 重建 → 继续飞；双树随时可丢弃重建
```

**未采纳的三种写回花招**（AI 曾提出、被 01:58 边界论断否掉，属实现层备选，非契约）：
alloc 实时置位 + free 延迟 / 双缓冲位图 A-B 切换 / generation+crc。
—— 这些只在「实现者选择让位图短暂落后」时才讨论，**不进入本文的设想本体**。
