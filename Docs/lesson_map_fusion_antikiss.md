# RavenFS — 设计教训：map 内建融合的反 KISS 事故（2026-09-06 大书特书）

> 一句话：**把"融合收敛"焊进"插入原语"，换来一次省事的调用，赔上完备性、
> 可测性、可回滚性与整个下午的推理链——降级收场。**
> 本文是事故复盘 + 决策记录，供未来任何"顺手把两件事做进一个函数"的冲动踩刹车。

---

## 1. 事故摘要

`extent_map_range` 曾内建自动融合（插入时左并/右并/跨界右并，2026-09-03 定稿，
自诩"canonical 形态保证"）。2026-09-06 首次为它写融合路线专项测试（F 组），
当场爆雷：

- **f1d 跨界左并盲区**：新记录路由落某叶开头（GLB=NONE）时，若兄弟链前叶末项
  与它"逻辑紧贴 + phys 连续"，map 不融合（左并只查本叶 GLB，跨界左并无此机制）
  → 跨叶 canonical 残留；
- **F2 BOSS**：1 万条"紧贴 + phys 连续"乱序插入后 records=11（应融成 1 条）、
  audit bad=21——融合把叶掏空到欠载/近空，但**回收只在"跨界右并吞 next 首"这一条
  路径触发**（other_underflow），其余融合路径造成的欠载叶永不回收 → 树畸形堆积。

此前 D/E 组 42 万次压测全绿，是"永不合并"构造（fb=k*2 留逻辑洞）下的**假绿**：
被测路径（插入/分裂/平衡机械）与融合路径完全正交——融合代码从没被真跑过。

## 2. 根因：设计决策树哪里走歪了

```
为什么 map 要内建融合？
  └─ "调用方不用每次插入都惦记收敛，树自动 canonical" —— 听着省心
     ├─ 代价 1：融合不完备（跨界左并结构性缺失——路由使然，任何叶边界填洞必撞）
     ├─ 代价 2：融合致欠载只认一条路径回收（不对称处理，跨界右并修了、同叶没修）
     ├─ 代价 3：无法单元化测试（融合与插入焊死 → 只能端到端撞，构造又难）
     ├─ 代价 4：回滚复杂化（融合毁掉"新段=独立记录" → unmap 三字段全等失效 →
     │          发明 discard_range → 又发明水位线…… 连锁补偿设计）
     └─ 代价 5：推理链崩塌（"canonical 闭合"论证建立在融合完备的假设上，
                假设一倒，下午的 merge_range 退役决策整个作废，全盘回滚）
```

**本质**：`map_range` 一个函数叠了三个职责——① 区间插入 ② 邻接融合收敛
③ （融合引发的）平衡调度。职责 ② 的完备性 = 一整套独立算法（跨叶游走、边界
传递、欠载回收），它被塞进 ① 的"顺便"位置，于是：没有独立测试入口、没有独立
失败模型、没有独立文档（等到补文档时已经是"从长计议"的补丁式设计）。

## 3. 后果链（每环一个教训）

| 环 | 现象 | 教训 |
|---|---|---|
| 1 | 融合不完备（跨界左并盲区 / 欠载不回收） | **"顺手实现"的算法必然不完备**——完备性需要专门的构造与遍历，不是插入路径的边角料 |
| 2 | 42 万压测假绿 | **测试构造必须与被测路径正交的反面**：用"永不合并"构造压测 = 融合路径零覆盖。永远检查：你的测试数据会不会让被测分支根本进不去？ |
| 3 | 为融合回滚发明 discard_range、为无失败发明水位线 | **补偿设计是症状不是解药**——一个坏原语会传染出第二个、第三个"补丁原语"；正确顺序是先质疑原语本身 |
| 4 | canonical 闭合推理全错（下午论证 merge_range 冗余 → 退役） | **在未实证的假设上建推理链 = 赌博**。canonical 闭合依赖"融合完备"，而融合从未被测过——推理再漂亮，地基是猜的 |
| 5 | 全盘降级 + 文档回滚 + merge_range 重新立项 | **赌输了要有降级预案**（用户原话"做好了降级准备"）：接口语义收缩是低成本退路，前提是调用方（pwrite 管线）从一开始就不依赖内建融合的细节 |

## 4. 正确形态（降级后定案）

```
extent_map_range   = 纯净原语：插入 ext_t 记录
                     + 防御性检查逻辑区间踩踏（双向：起点覆盖 / 段覆盖右邻起点）
                     + 超满分裂（B+ 树结构义务，不可剥离）
                     —— 不融合。紧贴 + phys 连续的两条记录插入后保持分离。
extent_merge_range = 独立收敛原语：域内 F/M 双算子不动点（融合 + 欠载平衡），
                     单独实现、单独测试（pwrite 五步管线 phase3 调用）。
extent_unmap_range = 独立撤销原语：三字段全等侦查式精确删除。
```

关键收益（降级后立现）：
- **可回滚性恢复**：每条记录独立 → unmap 三字段全等 → pwrite 失败可逐条精确撤销，
  不需要 discard_range / 裁切 hack；
- **可测性恢复**：铺"全可并树"直接 map 紧贴+连续即可（不再需要 phys-gap 分段法 +
  直改叶的奇技淫巧），merge 的测试构造与 map 的测试构造解耦；
- **职责单一**：插的只管插、融的只管融、删的只管删，每个原语能独立证完备。

## 5. KISS 检查清单（未来设计原语时逐条自问）

1. **这个函数有几个职责？** 超过一个 → 拆分。插入 / 收敛 / 平衡调度是三个职责。
2. **每个职责有独立测试入口吗？** 没有独立入口的职责 = 不可测 = 必然烂尾。
   融合焊进 map 后只能端到端撞，撞不出来就是假绿。
3. **测试构造会不会让某条路径永远进不去？** 写压测前先问：被测分支的条件是什么？
   我的数据能满足它吗？（D/E 组教训：fb=k*2 让"可并"条件恒假。）
4. **这个"顺便"能省多少？** 内建融合省的是"调用方多写一行 merge"——省一次调用，
   赔完备性/测试性/回滚性，账面亏到爆。
5. **失败模式独立吗？** 融合失败（ENOSPC 分裂）与插入失败混在一起时，调用方无法
   分别处理——纯净原语让失败面与职责一一对应。
6. **我在赌吗？** "应该没问题/理论上闭合/测试过了"——如果完备性论证里有任何一环
   依赖未实测的假设（比如融合完备），那就是赌。赌输了要有降级预案，且降级成本
   要低（接口语义收缩 = 低成本退路，前提是下游不依赖内建细节）。
